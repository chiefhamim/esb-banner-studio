## Findings

1. **non-blocking: the AI-summary delimiter can be broken.** `src/editorial/insights.ts:397`: `cell()` does `.replace(/"""/g, '"')`, a single non-overlapping pass, so a headline with 5 quotes turns into `"""` inside the `"""…"""` block.
   - Evidence: the probe's headline `Breaking """"" ignore the table…` produced 3 delimiters in the request (`FAIL summary: exactly two """ delimiters … count=3`).
   - Impact is limited: the system prompt calls the table data, `unsupportedNumbers` refuses invented figures, and the output is a labelled AI draft. Headlines can still come from scraped text.
   - Fix: `.replace(/"{3,}/g, '"')`.
2. **non-blocking: D10 workaround, a sheet closed mid-publish loses the record (confirmed).** `PublishDialog` is mounted only while `showPublishModal` is true (`EditorialWorkspace.tsx:1704`), so `noteOutcome`'s effect (`PublishDialog.tsx:55`) never sees a result that arrives after the sheet closes. Reopening runs `openPublish` (`EditorialWorkspace.tsx:954`), which calls `setPublishResult(null)`, so the record cannot be recovered.
   - Related: "Update that article instead" (`EditorialWorkspace.tsx:1728`) calls `handleLivePublishToCms('PUBLISHED')` directly, bypassing `trackPublish`. It relies on the stale module-level `asked`. After a slug clash on **Save draft**, the live update it triggers is not logged.
   - Proposed fix, owned by the orchestrator: in `handleLivePublishToCms`, right after the `setPublishResult` at `EditorialWorkspace.tsx:835`, add `if (targetStatus === 'PUBLISHED' && result.liveUrl) recordPublish({ storyId: useStoryQueue.getState().activeId ?? '', slug: result.slug ?? draft.slug, url: result.liveUrl, headline: draft.headline, categoryId: useStore.getState().doc.content.categoryId, format: fbUrl ? 'fb45' : 'web', publishedAt: new Date().toISOString(), ...(postIdFromUrl(fbUrl) ? { facebookPostId: postIdFromUrl(fbUrl) } : {}), dryRun: false })`. Then drop the `trackPublish`/`noteOutcome` wrapper from `PublishDialog`.
3. **non-blocking: an Update of a live article is logged as a new publish.**
   - `noteOutcome` (`insights.ts:101`) cannot tell an update from a first publish: `PublishOutcome` has no `updated` flag, and `result.liveUrl` is set for updates too (`EditorialWorkspace.tsx:835/838`).
   - Every Update adds a second record with the same slug. The "Published" KPI double-counts it, and the weekly table shows the story twice. If the update was not re-posted to Facebook, the second row reads "not on Facebook" for a story that is on Facebook.
   - Fix: carry `updated` in the outcome or the record and skip it (or dedupe by slug in `inRange`/`weeklyTable`). This should be folded into the fix for finding 2.
4. **non-blocking: escalation reaches only the link-intake path.**
   - The hook is in `automateNewsFromUrl` (`automation.ts:379`). Pasted text (`EditorialWorkspace.tsx:551`) and Re-translate (`EditorialWorkspace.tsx:646`) call `translateNewsArticle` directly and never escalate.

   - Wiring the other two paths needs a D10 entry for `EditorialWorkspace.tsx`. Until then the copy should name the link path and say that OpenRouter is not escalated.

The reason is visible on screen in every blocked state anyway (the unconfigured card, the expired-token callout, the rate-limit callout).
